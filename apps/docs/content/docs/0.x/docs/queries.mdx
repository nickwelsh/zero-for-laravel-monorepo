---
title: Queries
description: Declare live Inertia props or route-free query classes and execute typed queries through Zero.
---

Add `ZeroForLaravel\Concerns\HasZeroQueries` to participating models. Declare
queries in registered Inertia controller actions or standalone query classes,
not in browser-authored model selections:

```php
public function index(): \Inertia\Response
{
    return \Inertia\Inertia::render('tasks/index', [
        'heading' => 'Tasks',
        'tasks' => Task::zeroQuery()->orderBy('title', 'asc')->infinite(25),
    ]);
}
```

Constructing a query does not execute SQL. Generation analyzes the controller and
emits matching native TypeScript ZQL and authoritative PHP registrations. Input
comes from the declared route/FormRequest contract. Laravel validates and
authorizes each server invocation; the browser cannot supply an authoritative AST.

`zeroQuery()` returns a mutable `ZeroForLaravel\Query\ZeroQuery`, separate from
Eloquent's query builder. Use `where`, predicate callbacks, `with`, `whereHas`,
`orderBy`, `limit`, `start`, and `one`. Supported expression callbacks provide
comparisons, conjunction, disjunction, negation, existence, and literal comparisons.
Native `related` and correlated `EXISTS` are compilation details; the Laravel-facing
API uses `with` and `whereHas`, with no `related()` compatibility alias.

Use `infinite(size)` for an expanding live window and `paginate(size)` for cursor
pages. These require deterministic ordering. Raw cursor values retain storage
precision; decoded `Date` values are not used to reconstruct cursor boundaries.
Relationship queries retain native Zero semantics, including junction restrictions.

Normal route model binding still runs its database lookup. Returning an eligible
bound model as an Inertia prop converts it into a live singular query after the
controller executes. It does not eliminate Laravel binding or its authorization.

The live prop is absent from serialized Inertia page props, including initial
HTML. Reserved page metadata carries its identity. The [React adapter](./react.mdx)
injects its live value into the component; ordinary props remain ordinary props.

Generation supports a checked PHP subset around query declarations. Unknown calls,
unsupported control flow, or ambiguous output fail with source diagnostics. It
does not run arbitrary controllers to guess what queries they might return.

## Standalone query classes

Use a query class for reads owned by frontend components rather than an Inertia
page: search dialogs, pickers, detail panels, or one-shot reads. No route is
registered, and these queries do not appear in `route:list`.

```php
namespace App\Zero\Queries;

use App\Http\Requests\SearchTasksRequest;
use App\Models\Task;
use ZeroForLaravel\Query\ZeroQuery;

final class TaskQueries
{
    public function search(SearchTasksRequest $input): ZeroQuery
    {
        $validated = $input->validated();

        return Task::zeroQuery()
            ->visibleTo($input->user())
            ->where('title', 'LIKE', '%'.$validated['title'].'%')
            ->orderBy('title', 'asc')
            ->orderBy('id', 'asc')
            ->limit(20);
    }
}
```

`SearchTasksRequest` declares `title` as a required string and owns authorization.
Run `php artisan zero:generate` as usual. Public instance methods with an explicit,
non-nullable `ZeroQuery` return type are discovered in the application's production
Composer PSR-4 namespaces, including modules. `App\Zero\Queries` is a convention,
not a required location or class suffix. No base class or attribute is needed.
Static and nonpublic methods are not exported; abstract classes are not registered.
The existing `zero.discovery` selection applies to query classes as well as models
and tables, so include them when replacing automatic discovery with a list.

Generated modules mirror the PHP namespace and export each query as a callable
with a `.live()` selection:

```tsx
import { search } from '@/zero/App/Zero/Queries/TaskQueries';
import { useData } from '@nickwelsh/zero-for-laravel/react';

// One-shot native rows, waiting for server-confirmed results.
const rows = await zero.run(search({ input: { title: term } }), { type: 'complete' });

// Inside a React component: decoded live rows while the dialog is open.
const tasks = useData(search.live({ input: { title: term } }), { enabled: isOpen });
```

Native `useQuery`, `zero.materialize`, and `zero.preload` also accept the callable's
request. `InferQueryInput`, `InferQueryResult`, and `InferLiveQueryResult` infer the
same contracts as page queries. Includes, scopes, singular results, infinite
windows, and cursor pagination use the same checked query compiler.

Standalone reads use the existing Zero transport, not a new HTTP endpoint. They
require an authenticated Zero identity and use the endpoint's configured middleware.
Every server invocation runs its FormRequest's preparation, authorization, and
validation against that query's inputs, isolated from other queries in the batch.
Inputs must already match the validated canonical values used by generated ZQL;
normalization that changes them is rejected rather than silently diverging from
the browser. Public date inputs are `Date` objects, encoded before transport.

There is no page route middleware, route model binding, or route context. Accept
resource IDs as validated inputs and authorize them in the FormRequest; protected
row selections still require `visibleTo()` or their automatic visibility scope.
Route-dependent FormRequests must be adapted before reuse. Supported required
scalar and backed-enum parameters are also accepted directly; an ordinary
`Illuminate\Http\Request` parameter can supply the authenticated actor but is not
browser input. Unsupported guards, service calls, or control flow fail generation.
Neither generation nor a query transform instantiates or executes the query class.

## Mutable query composition

Builder calls mutate and return the same builder. Scope methods may return `void`
or the same builder, so both statement-style scopes and fluent chains work. Use an
explicit clone when creating independent branches:

```php
$base = Todo::zeroQuery()->where('list_id', $listId);
$active = (clone $base)->where('completed', false);
$completed = (clone $base)->completed();
```

`$active = $base` alone does not create a branch. Direct `Todo::completed()` and
`Todo::zeroQuery()->completed()` invoke the same `#[ZeroScope]` method. Dynamic
scope arguments are supported within the checked input/expression subset. The
Eloquent-like higher-order form `Todo::completed()->orWhere->assignedTo($userId)`
groups the next scope's conditions with OR. See [local scopes](./models.mdx#local-zero-scopes).

Nested predicate callbacks and higher-order OR scopes contribute **conditions
only**. A `withAttributes(...)` call inside one does not leak creation defaults
onto the parent builder. Root/local scope defaults are different: see
[creation precedence](./mutations.mdx#creation-defaults).

## Includes and parent filters

Use `with` to select related rows, and `whereHas` to keep only parents with a
matching related row. They are different operations:

```php
use ZeroForLaravel\Query\ZeroQuery;

$lists = TodoList::zeroQuery()
    ->whereHas('todos', fn (ZeroQuery $todos) => $todos->completed())
    ->with('todos', fn (ZeroQuery $todos) => $todos->completed()->orderBy('title', 'asc'));
```

This returns lists with at least one completed todo and includes their completed
todos. `with` by itself would not filter out a list with an empty matching include.
Relationship definitions come from supported Eloquent relationships between
opted-in models, not a `relations(...)` metadata list.

Each related query applies its model's global scopes independently. Parent scope
removal does not remove child scopes; remove a child's scope explicitly inside
its callback if trusted application logic requires it. Related builders do not
contribute creation defaults to the parent. Eloquent relationship calls such as
`$list->todos()` remain Eloquent and cannot invoke a Zero scope.

The compiler checks relationship keys, target enrollment, and constraints. It
does not auto-enroll target models, expose private correlation columns, or silently
ignore unsupported relationship constraints. See [model relationships](./models.mdx#eloquent-relationships-zero-includes)
and [membership-based visibility](./authorization.mdx#membership-based-todo-sharing).

## FormRequest inputs

Use a FormRequest for editable filters. A finite rule becomes both a literal
TypeScript union and a readonly options list on the injected live prop:

```php
// DashboardRequest
public function rules(): array
{
    return ['status' => ['sometimes', 'string', \Illuminate\Validation\Rule::in(['all', 'active', 'completed'])]];
}

// DashboardController
public function index(DashboardRequest $request): \Inertia\Response
{
    $values = $request->validated();
    $lists = TodoList::zeroQuery()->with('todos');
    if (isset($values['status']) && $values['status'] !== 'all') {
        $lists = TodoList::zeroQuery()->with('todos', fn ($todos) => $todos
            ->where('completed', $values['status'] === 'completed'));
    }

    return \Inertia\Inertia::render('dashboard', ['lists' => $lists->orderBy('name', 'asc')->infinite(25)]);
}
```

Direct `Rule::enum(BackedEnum::class)`, static `Rule::in([...])`, and string `in:`
rules supply finite options. Chained enum restrictions and dynamic option lists
are not inferred; use an explicit static list when needed. Options are values,
not translated labels. Laravel remains authoritative for authorization, validation,
and request preparation on each transform.

This example filters the included todos, not which lists are returned. Add a
matching `whereHas('todos', ...)` when the filter should also restrict the lists.

The [React adapter](./react.mdx#editable-live-inputs) exposes `inputs.values`,
`inputs.options`, `inputs.set`, and `inputs.reset`. Only FormRequest business
inputs are editable; route bindings and identity context remain fixed. Generated
native requests still accept the full declared route/request input contract.
