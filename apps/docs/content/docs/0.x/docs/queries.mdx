---
title: Controller queries
description: Declare immutable native ZQL queries alongside ordinary Inertia props.
---

Add `ZeroForLaravel\Concerns\HasZeroQueries` to participating models. Declare
queries in registered controller actions, not in browser-authored model selections:

```php
public function index(): \Inertia\Response
{
    return \Inertia\Inertia::render('tasks/index', [
        'heading' => 'Tasks',
        'tasks' => Task::zeroQuery()->orderBy('title', 'asc')->infinite(25),
    ]);
}
```

Constructing a query does not execute SQL. Generation analyzes the controller and
emits matching native TypeScript ZQL and authoritative PHP registrations. Input
comes from the declared route/FormRequest contract. Laravel validates and
authorizes each server invocation; the browser cannot supply an authoritative AST.

Queries are immutable. The PHP construction surface includes `where`, expression
callbacks, `whereExists`, `related`, `orderBy`, `limit`, `start`, and `one`.
Expression callbacks support comparisons, conjunction, disjunction, negation,
existence, and literal comparisons. Model visibility applies at every related scope.

Use `infinite(size)` for an expanding live window and `paginate(size)` for cursor
pages. These require deterministic ordering. Raw cursor values retain storage
precision; decoded `Date` values are not used to reconstruct cursor boundaries.
Relationship queries retain native Zero semantics, including junction restrictions.

Normal route model binding still runs its database lookup. Returning an eligible
bound model as an Inertia prop converts it into a live singular query after the
controller executes. It does not eliminate Laravel binding or its authorization.

The live prop is absent from serialized Inertia page props, including initial
HTML. Reserved page metadata carries its identity. The [React adapter](./react.mdx)
injects its live value into the component; ordinary props remain ordinary props.

Generation supports a checked PHP subset around query declarations. Unknown calls,
unsupported control flow, or ambiguous output fail with source diagnostics. It
does not run arbitrary controllers to guess what queries they might return.

## FormRequest inputs

Use a FormRequest for editable filters. A finite rule becomes both a literal
TypeScript union and a readonly options list on the injected live prop:

```php
// DashboardRequest
public function rules(): array
{
    return ['status' => ['sometimes', 'string', \Illuminate\Validation\Rule::in(['all', 'active', 'completed'])]];
}

// DashboardController
public function index(DashboardRequest $request): \Inertia\Response
{
    $values = $request->validated();
    $lists = TodoList::zeroQuery()->related('todos');
    if (isset($values['status']) && $values['status'] !== 'all') {
        $lists = TodoList::zeroQuery()->related('todos', fn ($todos) => $todos
            ->where('completed', $values['status'] === 'completed'));
    }

    return \Inertia\Inertia::render('dashboard', ['lists' => $lists->orderBy('name', 'asc')->infinite(25)]);
}
```

Direct `Rule::enum(BackedEnum::class)`, static `Rule::in([...])`, and string `in:`
rules supply finite options. Chained enum restrictions and dynamic option lists
are not inferred; use an explicit static list when needed. Options are values,
not translated labels. Laravel remains authoritative for authorization, validation,
and request preparation on each transform.

The [React adapter](./react.mdx#editable-live-inputs) exposes `inputs.values`,
`inputs.options`, `inputs.set`, and `inputs.reset`. Only FormRequest business
inputs are editable; route bindings and identity context remain fixed. Generated
native requests still accept the full declared route/request input contract.
