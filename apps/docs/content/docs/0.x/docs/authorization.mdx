---
title: Authorization, context, and global scopes
description: Resolve typed application context, preserve membership-based sharing, and authorize writes explicitly.
---

Use Zero global scopes for reusable read constraints and creation defaults. These
are Eloquent-like, removable query scopes, not immutable authorization rules.
Trusted application code owns the declarations; do not let browser input choose
which scopes to remove. Write policies, Gates, and FormRequest association checks
remain authoritative.

## Trusted application context

Define an application-owned, string-backed `App\Enums\ZeroContext` enum and
configure both `context` and `context_resolver`. The resolver exposes one public
method per enum case, annotated with `#[ResolvesContext(ZeroContext::USER_ID)]`.
See [the full configuration example](./configuration.mdx#typed-context-and-resolver).

Generation reflects resolver signatures without executing their methods. Native
`string`, `int`, `float`, and `bool` return types, including nullable variants,
define the generated context shape. Laravel resolves `Request` and service
dependencies when it resolves trusted values at runtime. Package runtime values
live in `ResolvedContext`; the application's enum is a declaration of keys, not
the runtime value bag.

```php
use App\Enums\ZeroContext;

$query = Todo::zeroQuery()->where('assigned_to', ZeroContext::USER_ID);
```

In supported Zero builder value positions, a configured context enum case is a
context reference. It is recognized **before** ordinary backed domain enums are
flattened into literal values. `ZeroContext::USER_ID->value` is the literal string
`'user_id'`, not a context lookup. An unrelated domain enum remains a literal.

The provider needs both native `userID` and typed `context`. Native identity is
independent of an application key named `user_id`; the package does not infer one
from the other. Browser values predict local queries/defaults. Laravel independently
resolves authoritative values from authenticated state. Validate tenant membership
before resolving a tenant value; never treat browser context as server authority.
Declare nullability intentionally and write predicates that handle it, rather
than assuming a nullable context key is an authenticated identity.

## Global scope registration

Implement the Zero-specific interface, not Eloquent's `Scope`:

```php
use App\Enums\ZeroContext;
use Illuminate\Database\Eloquent\Model;
use ZeroForLaravel\Query\ZeroQuery;
use ZeroForLaravel\Scopes\ZeroGlobalScope;

final class CurrentMemberships implements ZeroGlobalScope
{
    public function apply(ZeroQuery $query, Model $model): void
    {
        $query->where('user_id', ZeroContext::USER_ID);
    }
}
```

Apply it with `#[ZeroForLaravel\Attributes\ZeroScopedBy([CurrentMemberships::class])]`
on the model. Alternatively, register an instance or a named portable closure in
the model's boot registration:

```php
protected static function booted(): void
{
    static::addZeroGlobalScope(new CurrentMemberships);
    // Alternative to the class registration, not an additional requirement:
    // static::addZeroGlobalScope('current-user', function (ZeroQuery $query): void {
    //     $query->where('user_id', ZeroContext::USER_ID);
    // });
}
```

Registration order is inherited scopes, then model attributes, then boot
registrations. This registry order also determines global default precedence.
Scopes and closures must stay within the checked portable query subset; they are
not a server-only escape hatch for arbitrary SQL or PHP.

Remove a scope with `withoutGlobalScope(CurrentMemberships::class)` or
`withoutGlobalScope('current-user')`. `withoutGlobalScopes()` removes all global
scopes on that builder. Removing a scope removes both its conditions and its
creation defaults; it is not merely a change to SQL filtering.

Related models apply their scopes independently. Removing a scope from a parent
does **not** remove its children's scopes. A related callback can deliberately
remove that related model's scope:

```php
TodoList::zeroQuery()->with('memberships', fn (ZeroQuery $memberships) =>
    $memberships->withoutGlobalScope(CurrentMemberships::class));
```

This is an explicit application-level visibility decision, not permission to
expose arbitrary scope-removal controls to a client.

## Membership-based todo sharing

Do not replace shared-list access with an owner-only list filter. A membership
connects the current user to a list; collaborators may read lists they do not own.
Alongside `CurrentMemberships` above, define:

```php
final class AccessibleLists implements ZeroGlobalScope
{
    public function apply(ZeroQuery $query, Model $model): void
    {
        $query->whereHas('memberships')
            ->withAttributes(['user_id' => ZeroContext::USER_ID], asConditions: false);
    }
}

final class AccessibleTodos implements ZeroGlobalScope
{
    public function apply(ZeroQuery $query, Model $model): void
    {
        $query->whereHas('list');
    }
}
```

Attach the scopes to their respective opted-in Eloquent models (using the
relationship methods described in [models](./models.mdx#eloquent-relationships-zero-includes)):

```php
use ZeroForLaravel\Attributes\ZeroScopedBy;
use ZeroForLaravel\Concerns\HasZeroQueries;

#[ZeroScopedBy([CurrentMemberships::class])]
class ListMembership extends Model
{
    use HasZeroQueries;
    // Expose the required id, list_id, and user_id columns.
}

#[ZeroScopedBy([AccessibleLists::class])]
class TodoList extends Model
{
    use HasZeroQueries;
    // Define memberships() and todos(); expose their correlation keys.
}

#[ZeroScopedBy([AccessibleTodos::class])]
class Todo extends Model
{
    use HasZeroQueries;
    // Define list(); expose list_id and the other replicated columns.
}
```

The `whereHas` chain compiles into correlated existence predicates. Memberships
are constrained to the current user; lists require a visible membership; todos
require a visible list. The list's `user_id` is a **creation default only** because
`asConditions: false` avoids an owner condition. Shared lists therefore remain
visible to members who are not their creator. Create the creator's membership
explicitly in the same authorized mutation; a default does not create one.

`with('memberships')` includes matching rows; it does not replace the parent's
`whereHas('memberships')` filter. Related scopes apply independently in both
includes and parent filters. Register every target, and keep each model's column
allowlist narrow. Unsupported relationship constraints fail generation.

## Write authorization and defaults

Read visibility does not grant write permission. Keep policies and Gates in the
action or its FormRequest, and authorize foreign-key associations such as
`list_id` separately. Reload and lock state-dependent records before reauthorization
when needed. Ordinary Eloquent queries and relationships are not automatically
constrained by Zero scopes, so a policy must not assume that they are.

`withAttributes` supplies overridable creation defaults, not immutable ownership.
Defaults apply to Zero creates, never stamp updates, and do not modify normal
Eloquent creates outside Zero. Fields omitted from `$request->validated()` are not
caller input; trusted explicit creation data can override a default. Validate and
authorize any such override. See [creation defaults and precedence](./mutations.mdx#creation-defaults).

## Column exposure

Row visibility and column privacy are separate. Every replicated column on a
visible row is exposed through Zero. Use [column allowlists](./models.mdx#columns-and-privacy)
and the dedicated publication even when scopes filter rows. Generation rejects
missing required keys rather than quietly publishing private columns. `$fillable`,
FormRequests, and mutation policies do not hide replicated data.
