title: Policies and live visibility
description: Share Laravel policies across REST, Zero, and subscribed access errors with managed Casbin rules.
---

Laravel remains authoritative. Policies use normal discovery or `Gate::policy()`;
there is no separate Zero policy map. Current-user global visibility is opt-in.
The managed Casbin integration stores grants and role assignments in the database.
Its model file defines the matcher, role layout and effect, not individual grants.

## One policy for REST and Zero

```php
use Illuminate\Auth\Access\Response;
use ZeroForLaravel\Permissions\Casbin;

final class TodoListPolicy
{
    public function view(User $user, TodoList $list): Response
    {
        return Casbin::inspect($user, 'view', $list)->asNotFound();
    }
}
```

Add `HasPolicyVisibility` to the model for the ordinary Eloquent local scope and
`HasZeroQueries` when using Zero. Policies still work without a running Zero-cache
or generated query registry.

```php
// REST show: ordinary route binding, then Laravel Gate.
Gate::authorize('view', $list);
return new TodoListResource($list);

// REST index: filter before pagination, counts, or other collection operations.
return TodoListResource::collection(
    TodoList::query()->visibleTo($request->user())->paginate()
);

// Live index: same view policy; inaccessible rows are absent, not page errors.
return Inertia::render('lists/index', [
    'lists' => TodoList::zeroQuery()->visibleTo($request->user())->infinite(25),
]);
```

`visibleTo($user)` means the policy's instance `view` method, not `viewAny`.
An empty collection succeeds. Supply the actor explicitly; registered Zero queries
only accept the server-authenticated actor, not a browser-provided user ID.
Related selections and user-authored existence filters require their own explicit
visibility. Authorizing a root is not blanket permission for its related rows.

```php
TodoList::zeroQuery()
    ->visibleTo($request->user())
    ->with('todos', fn ($todos) => $todos->visibleTo($request->user()));
```

### Optional current-user global visibility

Use Laravel's ordinary `ScopedBy` attribute on each model that should always use
the current user's `view` policy. The package recognizes the same scope in Zero;
no separate Zero attribute or model method is needed.

```php
use Illuminate\Database\Eloquent\Attributes\ScopedBy;
use ZeroForLaravel\Concerns\HasPolicyVisibility;
use ZeroForLaravel\Concerns\HasZeroQueries;
use ZeroForLaravel\Permissions\VisibleToCurrentUser;

#[ScopedBy([VisibleToCurrentUser::class])]
class TodoList extends Model
{
    use HasPolicyVisibility;
    use HasZeroQueries;
}
```

When `Todo` opts in too, both `TodoList::with('todos')->get()` and
`TodoList::zeroQuery()->with('todos')` scope roots and related todos automatically.
This includes lazy/eager Eloquent relationships and Zero existence filters. Models
without the attribute retain the explicit `visibleTo($user)` contract.

The scope resolves the authenticated actor at query execution, never model boot.
Missing users fail closed with an authorization exception. Jobs and privileged
server code can select an explicit actor with `visibleTo($user)`, which replaces
the current-user default for that query, or remove the scope with Laravel's normal
`withoutGlobalScope(VisibleToCurrentUser::class)`. Removing it from a protected Zero
query still requires explicit visibility or a captured instance Gate; removal is
not a way to publish unrestricted protected data. Removing a root's scope does not
remove related models' scopes. Admin overrides still preserve caller filters.

As with any Eloquent global scope, route model binding now hides inaccessible
records before the controller runs, producing 404. Leave the scope off models
whose binding must reach a Gate to choose 403. This opt-in affects reads, bulk
updates/deletes, counts and relationships; it does not authorize writes or stamp
creation attributes. Maintained scopes require PostgreSQL 15+ and projections.

The default denied status is `permissions.denied_status` (403). Choose 404 globally
or override a policy response with `asNotFound()` / `asNotAuthorized()` (403, not
401). Normal Laravel route-binding failures still produce 404.

## Configure bindings and managed grants

```sh
php artisan vendor:publish --tag=permissions-config
php artisan vendor:publish --tag=permissions-migrations
php artisan migrate
```

The following binding uses the shipped `scoped-rbac-abac.conf`. All matcher attributes
must bind declared non-null database columns. Trim unused matcher branches and
bindings when the app only needs RBAC.

```php
// config/permissions.php
return [
    'connection' => null,
    'denied_status' => 404,
    'models' => ['default' => config_path('permissions/scoped-rbac-abac.conf')],
    'subject' => [
        'class' => User::class, 'prefix' => 'user:',
        'attributes' => [
            'department_id' => ['column' => 'department_id', 'type' => 'string'],
            'is_admin' => ['column' => 'is_admin', 'type' => 'boolean'],
        ],
    ],
    'resources' => [
        TodoList::class => [
            'type' => 'todo-list',
            'domain' => ['column' => 'id', 'prefix' => 'list:'],
            'attributes' => [
                'owner_id' => ['column' => 'user_id', 'type' => 'id'],
                'department_id' => ['column' => 'department_id', 'type' => 'string'],
            ],
        ],
    ],
];
```

Use the managed facade for every grant/role change, optionally inside the same
database transaction as business writes:

```php
Casbin::addPolicy('role:reader', 'list:7', 'todo-list', 'view', 'any', 'allow');
Casbin::addGroupingPolicy('user:42', 'role:reader', 'list:7');
Casbin::removeGroupingPolicy('user:42', 'role:reader', 'list:7');
```

`Casbin::model('name')` selects another configured model. Global roles use the
two-argument grouping layout. Domains isolate assignments and inherited roles;
ownership alone is not a grant. The rule's condition is interpreted by the matcher,
not by a reserved magic role name.

Before serving portable queries, run `php artisan permissions:rebuild` on PostgreSQL
15+. This transaction installs/backfills private subject, grant and resource-key
projections plus monitored-column database triggers. Direct business SQL and mass
updates therefore maintain authority facts too. Source rows, rules and projections
must share one configured connection. Managed writes participate in the caller's
transaction. Take `ProjectionManager::lock()` before model-row locks when combining
permission and business changes; retry a failed transaction, not partial writes.
Do not write raw `permission_rules`, private projections, or an independently cached
Casbin enforcer around the managed integration.

Rebuild after changing model files, bindings or authority schemas; regenerate
contracts and synchronize the dedicated publication. Missing/stale projections and
stale generated fingerprints fail closed. Authorization-only columns/tables are
replicated to trusted zero-cache, but excluded from browser schemas and row results.

## Portable compiler boundaries

The compiler analyzes the policy source; it never runs a fake resource and guesses
SQL from a boolean. Supported policy methods directly return `Casbin::inspect()`
with a literal action and optional denial override. Literal allow/deny responses
are supported too. Normal Laravel registration determines the effective policy.

Supported model families are direct ACL, global RBAC, domain RBAC, role-free ABAC,
and RBAC/ABAC hybrids. The supported layouts use `r = sub, obj, act` or
`r = sub, dom, obj, act`, corresponding exact policy selectors and optional positive
`g(subject, role[, domain])`. Role graphs must be acyclic and at most eight levels
deep. Effects are allow-only or allow with deny override; no matching allow denies.

Matchers support typed AND/OR/NOT, exact selectors, non-null resource comparisons
with literals, owner equality with subject ID, subject attributes against literals,
and resource/subject attribute equality (for example departments). Types are IDs,
strings, booleans and JavaScript-safe integers. Equality stays type-consistent.
Cross-row ordering such as `resource.level <= user.clearance` is not representable
live in Zero 1.11.3 and rejects rather than capturing stale user attributes.

`eval`, custom functions, regex/pattern roles, nullable/JSON/float/date comparisons,
time-dependent grants, priority effects, negated role reachability and arbitrary
PHP lookups/hooks are server-only. They cannot be used in `visibleTo()` or browser
predictions. Custom Eloquent visibility scopes and unrepresentable global scopes
also reject; the compiler never silently substitutes another implementation.

### A live super-admin override

The narrowly supported ordinary policy hook is:

```php
public function before(User $user, string $ability): ?bool
{
    return $user->is_admin ? true : null;
}
```

`is_admin` must bind a non-null database boolean. This bypasses even Casbin denies,
but keeps caller filters, tenant boundaries, route constraints and soft deletes:
`existing filters AND (live_admin OR (allow AND NOT deny))`. A regular Casbin admin
role remains subject to the Casbin effect. Removing the flag updates subscriptions
without a retransform. Other policy hooks and global Gate hooks reject on portable
paths, including hooks registered after generation.

## Subscribed show errors and callbacks

An ordinary show route needs no query wrapper:

```php
public function show(TodoList $list): \Inertia\Response
{
    Gate::authorize('view', $list);
    return Inertia::render('lists/show', ['list' => $list]);
}
```

The generator captures this supported unconditional instance Gate. Initial requests
use normal Laravel/Inertia exception handling. Named query transforms replay binding,
middleware and the real Gate without rerunning controller effects. Their native
Zero predicates also include the live guard, including descendant queries.

The Inertia adapter subscribes to reserved access queries on Zero's existing
WebSocket. Laravel reloads the actor and replays the route middleware, binding and
Gate under the permission transaction lock, then stores a safe status row. Private
revision predicates remove obsolete allowed and denied results; the adapter batches
fresh checks when the replicated revision changes. No SSE connection, browser
authorization fetch or polling PHP worker is required.

Protected content waits for a complete current-generation status and business
query. Disconnect, identity/input changes and visibility restoration invalidate old
approvals. Checks renew after 15 seconds and expire 20 seconds from their monotonic
request start, so delayed responses cannot extend stale approval. These renewals
cover middleware dependencies that do not produce database invalidations. Database
revocation follows commit and normal replication/network delivery, not zero latency.

```tsx
const livePages = createInertiaAdapter(bindings, {
    access: {
        onRevoked: ({ status, query, prop }) => {
            router.visit('/lists');
            toast.error('This list is no longer available.');
        },
        // Optional: onError(status), onPending().
    },
});
```

Confirmed loss unmounts the protected page before the callback. Callbacks fire once
per allowed-to-denied transition, not on initial denial, network failure, an obsolete
route event or an empty collection. Deleted and inaccessible resources share the
same concealed 404 state. An unavailable expected singleton blocks while rechecking.
A disconnected control channel is unknown and blocks protected rendering until
fresh validation. Previously downloaded/offline data cannot be erased; native data
predicates, not callbacks, prevent future unauthorized streaming.

Run the permission migrations, rebuild the projections, regenerate the client and
synchronize the Zero publication when upgrading. The native transport uses two
physically safe root tables and one private check table; old ephemeral SSE watches
are removed by the upgrade migration. Check generations are owner/session/context
scoped, quota-limited and cleaned up with bounded work. Subscriptions release on
unmount; periodic renewal does not remount healthy business queries.

The revision is deliberately global, matching the previous notification scope:
unrelated permission changes can trigger rechecks and reveal change timing, but
never expose policy contents or another subject's status. This is not strict
per-user timing isolation. Zero-cache still makes brief internal Laravel callbacks
and each fresh check writes status/metadata rows. The private cache API key never
belongs in the browser. `access.endpoint` and SSE polling/heartbeat settings no
longer exist.

## Optional current-user UI predictions

Use `Predictions::forUser($request->user(), $abilities)` from an authenticated,
application-registered endpoint when UI predictions are needed. The server chooses
the actor and supported abilities; there is no arbitrary-subject permission route.
Opt into safe attributes explicitly:

```php
'predictions' => [
    'abilities' => [TodoList::class => ['view']],
    'subject_attributes' => ['department_id', 'is_admin'],
    'resource_attributes' => [TodoList::class => ['id', 'owner_id', 'department_id']],
],
```

The feed contains applicable effective grants and validated predicate descriptors,
not the raw graph or another user's memberships. Abilities needing an unexposed
attribute are omitted. Feed endpoints must return private/no-store responses and
refresh on permission changes. Do not persist one identity's feed for another.

When `predictions.abilities` is nonempty, the package registers authenticated
`GET /zero/permissions` (under `zero.route_prefix`). It takes no query parameters
and returns only the configured abilities for the authenticated user.

`predictPermission(feed, resourceClass, ability, row, authenticatedUserId)` returns
`true`, `false`, or `undefined` for an unavailable or malformed prediction. It
checks identity and scalar types before evaluation; it cannot detect a same-user
feed that an application has not refreshed. These are UI hints only; never accept
a browser prediction as authorization for reads, writes or watch registration.

## Migrating the previous API

Remove model `zero()` methods and `ZeroDefinition` imports. Move publication to
`zero.models` or trait discovery, deliberate public reads to `zero.public_models`,
creation defaults to `withAttributes()` with typed application context, and search
to `zeroSearch()` or the registered search integration. Defaults do not enforce
ownership: explicit creation attributes override defaults, and updates are not stamped.
Replace scalar/relation authorization and server-scope closures with ordinary
policies plus explicit visibility on every protected query path. Backfill old ACL
tables into managed grants; do not maintain two permission authorities. Use
`Mutation::server(...)` with disabled optimism for permission writes. Rebuild
projections, regenerate paired PHP/TypeScript and review publication changes before
deployment. See the todos example for transactional share/unshare and ACL backfill.
