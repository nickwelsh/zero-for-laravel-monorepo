Use `->authorizeRelation('memberships')` to require at least one related row
that is visible under the related model's own authorization. For a shared list,
configure memberships with `->authorize('user_id', '=', ContextField::UserId)`
and the list with `->authorizeRelation('memberships')`. Todos can then use
`->authorizeRelation('list')` to inherit access to their parent list.

These predicates compile to correlated `EXISTS` queries in both Laravel and the
native client. Multiple scalar and relationship authorization attributes combine
with AND. Authorization relations do not automatically become allowed includes;
declare includes separately. Register every target model. Cycles and authorization
paths deeper than eight relationships fail generation. Write policies and
FormRequests still control mutations and association changes.

See [the authenticated todos example](https://github.com/nickwelsh/zero-for-laravel-monorepo/tree/main/examples/todos) for shared lists,
PostgreSQL, and Herd HTTPS setup.

## Trusted context and server scopes

```php
return ZeroDefinition::make()
    ->authorize('user_id', '=', ContextField::UserId)
    ->fillFromContext('user_id', ContextField::UserId)
    ->relations('list');
```

Use `publicReads()` for explicitly public models, or `authorizeRelation('list')`
to require a related row visible under that model's own definition. These
constraints are generated for local queries and independently enforced by Laravel.
Context fills apply on create, are resolved separately on client/server, and are
excluded from caller-writable fields. Custom context keys can use string references.
The server context resolver must derive their values from authenticated state.

For runtime PHP, use a mandatory server scope:

```php
->enforceServerScope(
    function (ZQLBuilder $query, ZeroContext $context): void {
        $query->whereExists('list', fn (ZQLBuilder $list) => $list->where(
            fn (ZeroOperator $op) => $op->or(
                $op->cmp('user_id', $context->get('user_id')),
                $op->exists('shares', fn (ZQLBuilder $share) =>
                    $share->where('user_id', $context->get('user_id'))),
            ),
        ));
    },
    relations: ['list'],
)
```

Register `shares` on the list definition with `->relations('shares')` or through
its own scope's `relations` argument. This declares schema dependencies without allowing client
includes. Every related target must be registered and define its own visibility.
Scopes also apply to included rows and relationship predicates. Conditions within
a scope can use OR; the mandatory scope as a whole is ANDed with user filters.
An empty scope is an error. Missing required context denies access.

Callbacks execute with fresh trusted context during server query compilation,
never during generation. Their PHP source is not exported. Zero permits server
queries to add permission constraints absent from the local implementation.
Local queries can still match other already-synced authorized rows, so mirror
predicates with `authorize`/`authorizeRelation` when exact local behavior matters.

## Write authorization

Read visibility does not grant write permission. Controller mutations must call
the appropriate Laravel policy or gate, in the action or its FormRequest.
FormRequests authorize and validate the payload separately, including foreign key
association permissions. See [mutations](./mutations.mdx) for complete examples.

## Column exposure

Read authorization decides which rows a client may receive. Every selected column
on those rows is exposed through Zero, so define [column privacy](./models.mdx#columns-and-privacy)
as well. A nonempty Eloquent `$visible` list restricts columns by default;
`ZeroColumns` can supply a separate explicit replication allowlist.

Keep ownership fields used by `authorize()` and `fillFromContext()` in that
allowlist. Generation fails if those fields or registered relationship keys are
excluded. `$fillable` and mutation policies do not hide replicated columns.

The browser's context supplies local values and optimistic fills. Laravel resolves
a fresh `ZeroContext` through `zero.context_resolver`; derive custom tenant values
only after checking the authenticated user's membership. Never trust a tenant ID
or user ID supplied in the browser to establish server access.
