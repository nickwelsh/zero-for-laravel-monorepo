---
title: Shared business operations
description: Compose transaction-aware helpers, preference writes, and server-only effects.
---

Business actions use `#[ZeroMutation]` controller methods.
Use explicitly disabled optimism for arbitrary authoritative PHP, or associate a
custom native projection through the generated factory.

Mark portable helper classes `#[ZeroShared]`. Only methods reachable from an action
are compiled. Helpers can receive `Mutation`, models, and supported scalar inputs.
Dynamic dispatch, recursive calls, arbitrary constructors, and unknown dependencies
fail generation with source diagnostics.

Transaction primitives include:

- `reloadForUpdate`: authoritative reload and row lock; native transaction read locally.
- `findUnique`: read by an actual unique key in the current transaction.
- `insertUnlessExists`: create only when no row with that key exists; preserve existing opt-outs.
- `upsertUnique`: insert or update only the explicitly supplied fields.

Unique keys require a real unconditional unique index. PostgreSQL conditional
insertion uses savepoint conflict recovery so a competing opt-out is not overwritten.
Partial, expression, nullable, or deferred unique-key assumptions are unsupported.

Capture the old assignee before updating a mutable model. Distinguish an absent
input key from explicit null with `array_key_exists`. A helper after the update
sees the updated transaction state. Check visibility for the intended recipient,
not only the actor; a failed authoritative check rolls back earlier writes.

Known Gate calls and explicit `Mutation::server` void closures remain server-only.
A server-only result cannot silently feed a shared write. Preference rows are
transactional state; sending notifications is an external effect. Persist an
application-owned outbox row atomically for durable delivery, and make its worker
idempotent. `afterCommit` alone does not guarantee delivery after a process crash.
