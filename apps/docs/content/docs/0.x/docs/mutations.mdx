title: Controller mutations
description: Compile typed controller actions into native optimistic and authoritative execution.
---

Explicitly annotate an action on a registered Laravel route:

```php
use ZeroForLaravel\Attributes\ZeroMutation;

/** @return array{id: string} */
#[ZeroMutation]
public function store(StoreTaskRequest $request): array
{
    $task = Task::create($request->validated());

    return ['id' => $task->id];
}
```

The authoritative FormRequest retains preparation, authorization, rules, and
validation hooks. Arbitrary FormRequest hooks and Eloquent events do not
automatically run in optimistic JavaScript. Generated prediction covers only the
checked portable subset; use custom or disabled optimism when nonportable PHP
changes the intended local result.
Annotated actions are native-only: ordinary HTTP requests to their route return
405 instead of bypassing stable preparation or invoking a second write path.
Real route middleware and binding run at the authoritative boundary. Call Gates
and policies explicitly in the action or its request; an attribute is not a grant
of permission. Reload and lock state-dependent bound records with
`$mutation->reloadForUpdate($task)` before reauthorization and writes.

One checked operation tree generates native client execution and authoritative
Eloquent execution. Prepared IDs and timestamps are reused across replay and
delivery. Metadata stays separate from mass-assignable input. Unsupported shared
PHP fails generation rather than silently disappearing.

## Optimism strategies

- `#[ZeroMutation]`: generated prediction from supported PHP.
- `#[ZeroMutation(optimism: 'custom')]`: an explicitly supplied native projection.
- `#[ZeroMutation(optimism: 'disabled')]`: enqueue without speculative writes.

All three use the same native protocol, validation, results, and lifecycle. Pass
custom projections to the generated `createControllerMutationBindings` factory.
When a custom action exists, the React module exports `createZeroBindings(projections)`
instead of constructing a provider without the required projections. Call it once
in an application-owned module and export its `ZeroProvider` and `actions`.
Key each projection by the imported action's literal `action` property, for example
`createZeroBindings({ [notify.action]: async ({ tx, args }) => ... })`, rather than
typing a PHP controller path by hand.
Declare their client result independently when it differs from the server result.
Missing required bound rows produce the declared pre-write no-op prediction;
the valid intent still reaches Laravel.

## Client invocation

```tsx
import { useControllerMutation } from '@nickwelsh/zero-for-laravel/react';
import { store as create } from '@/zero/App/Http/Controllers/TaskController';

const createTask = useControllerMutation(create);
const saved = await createTask({ title: 'A task' });
console.log(saved.id);
```

Exports follow the PHP namespace and method name. Each controller module also
exports named input and result types, such as `StoreInput` and `StoreResult`.
The same imports work with custom optimism: the hook uses the bindings installed
by the current generated `ZeroProvider`, including its custom projections.

## Prepared fields

Generated creates prepare identities and time **before** calling `zero.mutate`.
`HasUuids` selects UUID generation; `HasUlids` selects ULID generation. Eloquent's
timestamp settings determine the created/updated columns, including renamed
`CREATED_AT` and `UPDATED_AT` columns. Auto-incrementing keys are not supported
for generated creation. These values stay outside FormRequest business input:
forms send fields such as `title`, not required IDs or timestamps.

Preparation runs once per submission. The frozen native arguments carry the same
values through optimistic execution, replay, and authoritative PHP execution.
Updates preserve creation time and use the prepared time for the updated column.
Server authorization and format validation still apply; client time is not a
trusted audit clock. Arbitrary server-only Eloquent creates in custom/disabled
actions are not automatically transformed into client-prepared creates.

Override generators globally when constructing the generated provider:

```ts
import { v7 as uuid } from 'uuid';
import { createZeroBindings } from '@/zero/generated.react';

export const { ZeroProvider } = createZeroBindings({ uuid, now: () => new Date() });
// With custom optimism: createZeroBindings(projections, { uuid, now: () => new Date() }).
```

Or pass overrides as the hook's third argument:
`useControllerMutation(create, {}, { uuid, now: () => new Date() })`.
The supported generators are `uuid`, `ulid`, and `now`. Overrides must return valid,
distinct identities and a valid nonnegative date. Never generate values inside an
optimistic projection: Zero can replay it more than once.

Supply route arguments for bound actions. For direct native control, prepare once
with a binding from `createControllerMutationBindings`, using
`binding.prepare(input, routeArguments, preparation)`, then call `zero.mutate(request)`.
`.client` means local application; `.server` means authoritative outcome. For
data-returning actions, parse result data with the generated client/server schemas.
For redirect actions the raw native result carries an internal navigation
instruction, not a value to pass to the public void result schema. Use the form
or `.mutate()` below to handle it. Models and HTTP responses are not implicit
result contracts.

The hook tracks pending state, field errors, local application, server acceptance,
and committed-but-undecodable results separately. Unmounting the hook stops its
observer, not the queued write. Use the generated form or direct action below for
automatic navigation. Neither the hook nor a replayed mutator drives the router.

Business changes, native progress, and returned data commit atomically. Application
rejections roll back business writes and persist an error outcome. Duplicate
delivery does not rerun the action; a lost callback response can recover through
native persisted results. These are not durable JavaScript promises across reloads.

## Migrate an Inertia form by changing two imports

With a generated `ZeroProvider` and the Zero Inertia page adapter installed, change
the form and controller imports. Keep the named inputs, submit button and render props:

```diff
-import { Form } from '@inertiajs/react';
-import TodoController from '@/wayfinder/App/Http/Controllers/TodoController';
+import { Form } from '@nickwelsh/zero-for-laravel/react';
+import TodoController from '@/zero/App/Http/Controllers/TodoController';
```

```tsx
<Form {...TodoController.update.form(todo.id)}>
    {({ errors, processing }) => (
        <>
            <input name="title" defaultValue={todo.title} />
            {errors.title && <p role="alert">{errors.title}</p>}
            <button disabled={processing}>Save</button>
        </>
    )}
</Form>
```

`store.form()` takes no route arguments. A single binding accepts its scalar route
key, a model containing that key, or a named argument. Use named arguments for
nested routes. To submit without a form, `await TodoController.destroy.mutate(todo.id)`.
These helpers require an unambiguous registered route and enqueue one native write.
Formbraid is a separate, optional API.

The form reads successful DOM controls, including the submitter, runs `transform`,
normalizes values using the request contract and validates before enqueue. An
unchecked checkbox is absent, not `false`; declare optional flags accordingly.
Mounted forms call `onSuccess` on server acceptance, not local application.
Use the `.mutate()` promise when the result must outlive the form. Forms can
show field errors and use `reset`, `defaults` and `isDirty`. No files, upload
progress, HTTP visit options, cancellation or Precognition: keep using ordinary
Inertia routes for forms that need those features.

### Navigate after a local write

```php
#[ZeroMutation]
public function store(StoreTodoRequest $request): RedirectResponse
{
    $this->authorize('create', Todo::class);
    $attributes = $request->safe()->except(['open_after_saving']);
    $todo = Todo::create($attributes);

    return $request->boolean('open_after_saving')
        ? to_route('todos.show', ['todo' => $todo])
        : back();
}
```

For this example, declare `title` as a required string and `open_after_saving`
as an optional boolean in the FormRequest. Keep `title` writable on the model;
the checkbox controls navigation and is never a Todo attribute.

`zero:generate` reads the controller source and checks the types of the request
and model. It emits the same operations into `generated.mutations.ts` and the
PHP mutation registration. For this action they are, in execution order:

1. `guard`: Laravel runs `Gate::authorize('create', Todo::class)`. The browser
   does not evaluate the policy to decide whether it can predict the insert.
2. `safeExcept`: copy the validated fields except `open_after_saving` into
   `attributes`. Generation rejects unknown or dynamic exclusion keys.
3. `create`: insert those attributes into `todos` using the ID and timestamps
   prepared for this submission. The generated `s0` names this create instruction,
   not a row. Each submission gets its own ID; replay uses the same one.
4. `redirectWhen`: a checked box yields `visit` with route `todos.show` and the
   new model's `id`; an unchecked box yields `stay`. The compiler checks the
   literal GET route name and its parameters. A custom request hook that can
   change the boolean makes the client wait for Laravel to choose the branch.

`back()` means stay: it does not go back in history or drop query parameters.
`to_route()` names a registered GET route. The redirect is an instruction, not
an HTTP response, flash payload, or public return value. The form and `.mutate()`
observe it in the originating tab. When a generated create redirects to the new
model's primary key, the normal show page reads that row from Zero immediately.
Use the generated `navigation` with `createInertiaAdapter`. There is no second
component or prop built from the form. The local query observes the prepared ID,
timestamps and defaults, and switches to the authorized server stream after the write.
Returning to a previously synchronized list after delete reads the same replica;
it does not require keeping the list mounted. Zero reconciles either write with Laravel.
Pages that need server props use a GET. Neither path pushes the same
history entry twice. A server-only key, missing local row or non-predictable
destination waits for the authoritative result.
Use `#[ZeroMutation(navigateAfter: 'server')]` to delay **navigation** for a
sensitive action without disabling its optimistic write. See [how Show reads the
new row](./queries.mdx#return-a-route-bound-model) and [when its permission watch
starts](./authorization.mdx#when-the-permission-watch-starts).

### What happens if Laravel rejects the create?

Zero rolls back the optimistic insert. The `Form` restores the draft separately:
it captured the named controls as `FormData` _before_ `transform` or boolean
normalization. That is why it can restore a checkbox that was never in the row.

- **Still on the predicted Show page:** the adapter replaces that history entry
  with the exact submit URL, including its filters. On mount the matching form
  consumes the draft once, restores the controls and displays the server's field
  errors. The original defaults still apply, so the user can edit or reset the draft.
- **Stayed on the index:** the form is still mounted. It displays the error in
  place; there is no draft handoff or history change.
- **Already navigated elsewhere:** the adapter leaves the current page alone and
  reports “A previous change could not be saved.” Handle `zero:mutation-error`
  on `window` and call `event.preventDefault()` to replace the default notice.

The handoff lives in the current provider's memory and matches the original URL,
controller action and bound route arguments. It does not survive a full reload or
retry the submission. A disconnected, pending write is not a rejection. If the
write committed but the client could not apply the response, do not resubmit it.

## Formbraid 0.3

Use Formbraid's normal descriptor API in a React 19 app:

```tsx
import { store, update } from '@/formbraid/zero/App/Http/Controllers/TodoListController';
import { Form } from '@/formbraid';

<Form form={store} />;
<Form form={update({ list: list.id })} defaultValues={{ name: list.name }} />;
```

Install `formbraid/laravel`, `@formbraid/core`, and `@formbraid/react` at `^0.3.0`,
and `effect` at `4.0.2`. Run `php artisan formbraid:init` to scaffold the
application-owned registry and components. Register a build-only Zero producer
instead of the scaffold's HTTP Laravel producer:

```php title="config/zero.php"
'formbraid' => [
    'enabled' => true,
],
```

```ts title="resources/js/formbraid/zero.ts"
import type { Integration } from '@formbraid/core/vite';

export default {
    name: 'zero',
    registry: new URL('./index.ts', import.meta.url),
    metadata: new URL('./_metadata.json', import.meta.url),
    command: ['php', 'artisan', 'zero:generate'],
    watch: ['app/**/*.php', 'routes/**/*.php', 'config/zero.php', 'config/formbraid.php'],
    outputs: ['resources/js/formbraid/zero/**', 'resources/js/zero/**', 'app/Formbraid/FormField.php'],
} satisfies Integration;
```

```ts title="vite.config.ts"
import { vitePlugin as formbraid } from '@formbraid/core/vite';
import zeroForms from './resources/js/formbraid/zero';

// Alongside the application's other Vite plugins:
formbraid({ integrations: [zeroForms] });
```

Vite inspects the component registry and writes metadata before running Artisan.
With `formbraid.enabled`, `zero:generate` reuses Formbraid's request extraction, field/group generation,
component enum, and hash-owned publication. It refreshes native Zero contracts and
the React provider, then emits definitions and callback-backed controller forms
under `zero.formbraid.output` (default `resources/js/formbraid/zero`). Only
`#[ZeroMutation]` actions with one FormRequest produce forms. Parameterless actions
export descriptors; actions with model/scalar route arguments export factories.
There is no Zero-specific form hook or replacement `Form` component.

`zero:dev` includes forms in its startup generation. `zero:generate --check` checks
them without writing files. The explicit `zero:formbraid` command generates both
contracts and forms even when the enable flag is off, and accepts the same
`--check` and `--output` options. Keep the Vite integration for regeneration after
edits and for producing component metadata before either Artisan command runs.

Zero actions are native-only: do not use Formbraid's Fetch/Inertia controller
descriptors for them. Ordinary HTTP forms may still use the Laravel producer in a
separate output directory.

Formbraid owns the editable draft, validation, errors, defaults, and submission
lifetime. Zero owns preparation, optimistic replay, and the durable write. The
generated callback resolves the application's connection only at submission,
reuses its registered bindings/preparation, and retains the authoritative result type.

`formbraid.runtime` is an import path, not another process to run. A generated form
calls `controllerRuntime()` at submission to obtain the active client, registered
actions, and ID/timestamp preparation. With `runtime` left `null`, it imports that
function from `zero/generated.react.ts`.

When mutations use custom optimistic code, the generated React module exports a
factory instead of ready-made bindings. Call it once in an application module:

```ts title="resources/js/zero/bindings.ts"
import { createZeroBindings } from './generated.react';
import { projections } from './optimism';

export const { ZeroProvider, controllerRuntime } = createZeroBindings(projections);
```

Here `projections` contains your client-side mutation implementations. Set
`zero.formbraid.runtime` to `'resources/js/zero/bindings.ts'` and use `ZeroProvider`
from that same module in your application. Generated forms import its
`controllerRuntime`, so both use the bindings with your custom optimistic code.
Do not create a second set of bindings just for the forms.

Static descriptors require one active Zero session per binding; ambiguous clients
are rejected rather than selecting another user's connection. Separate
applications can use separate binding instances.

Initialize defaults through `<Form defaultValues={values} />`. Formbraid's own
`useForm(store, options)` remains available when programmatic reset or instance
access is useful. Use a key or explicit reset when switching records; rerenders
must not reset edits.

Success includes the decoded authoritative result as `result.value` in Formbraid's
`onResult`. Local optimistic completion alone does not settle the form. Laravel
field/root errors and generated input-codec errors become `invalid`; other errors
become `failure`. A committed result-decoding failure remains a
`MutationResultError` with `committed: true`: show the warning without retrying the
write automatically. Cancellation or unmount stops observation and suppresses
late outcomes, but cannot undo an enqueued mutation. An already-aborted submission
does not enqueue a write. This transport does not report upload progress or add a
file-upload path to Zero's JSON mutation protocol.

The todos example consumes generated create-list and add-todo descriptors with
application-owned components. Optional producer utilities live in
`@nickwelsh/zero-for-laravel/formbraid`; application components need not import them.
Zero's ordinary entry points do not load Formbraid or Effect.

### Query-backed options

Declare an option query directly in the mutation FormRequest's `fields()` map.
References supply their own inputs; there is no callback signature or separate input map:

```php
use Formbraid\Laravel\Field;
use Formbraid\Laravel\OptionInput;
use ZeroForLaravel\Formbraid\ZeroOptions;

public function fields(): array
{
    return [
        'other_party_id' => Field::make('ComboboxField')->options(ZeroOptions::query(
            Party::zeroQuery()
                ->where('organization_id', OptionInput::field('organization_id'))
                ->where('id', '!=', OptionInput::context('party'))
                ->where('name', 'ILIKE', ZeroOptions::contains(OptionInput::value()))
                ->orderBy('name')->orderBy('id')->limit(20)->get(),
            value: 'id', label: 'name',
            resolve: Party::zeroQuery()
                ->where('organization_id', OptionInput::field('organization_id'))
                ->where('id', '!=', OptionInput::context('party'))
                ->find(OptionInput::field('other_party_id')),
            authorize: ['party' => 'view'],
        )),
    ];
}
```

`value()` is the control-local value passed to `useFieldOptions({ value })`, such
as typed filter text. It is **not** the submitted field ID. `field(path)` reads a
current form draft value. `context(key)` reads a named model/scalar argument of the
mutation action, captured by its generated form factory, for example
`addRelation({ party: party.id })`. Pass canonical primary IDs for model context,
not route slugs or custom route-binding values. Context is untrusted input, never
an authorization claim. Model context requires an explicit portable read-policy
ability in `authorize`; that policy is checked on every transform and remains in
the live permission guard. Protected root rows automatically use the authenticated
actor's visibility; related protected paths still require explicit visibility.

`ZeroOptions::contains()` makes a literal substring pattern: `%`, `_`, and `\` in
the typed value are escaped. Without it, operands keep the query operator's normal
meaning. Listing requires an explicit literal limit from 1 through 100 and ordering
that includes the model's primary key. The optional `resolve` query must end in
`first()` or `find()` and must not use `value()`. Give it the same eligibility/dependency filters,
but compare the ID with the selected draft field. It resolves labels independently
of the current search or result window, even while the picker is closed. Without
a resolver, an existing selection is reported as unavailable. No dependency change
silently clears the selected ID; that policy belongs to the application.

Generation emits paired registered queries plus stable Formbraid source bindings.
`zero:formbraid` attaches them automatically with `withOptionSources`; applications
do not write query-specific React components. Put the generated `ZeroProvider`
(and any access boundary) **above** the Formbraid form, since adapters mount at the
form level, not inside the picker.

A reusable registry control consumes only Formbraid APIs:

```tsx
const field = useFieldContext<string | null>();
const [filter, setFilter] = useState('');
const { listing, selection } = useFieldOptions({ value: filter, enabled: open });

// Render listing.items in your combobox; render selection.item when complete.
// On selection, store the ID, never the filter or label:
field.setValue(String(item.value));
```

The Zero adapter uses ordinary `useData` subscriptions with no additional cache.
Missing or invalid draft inputs produce idle state; empty strings, zero, and false
are not treated as missing. Pending/partial or failed data is not published as
selectable options. Option reads validate only their compiled scalar input
contracts; they do not execute the mutation request's hooks, full validation, or
write-route middleware. Enforce read permissions through visibility and explicit
read guards, and keep authoritative relationship validation in the mutation.
Only supported scalar references and concrete field paths are accepted; wildcard
repeater references, pagination/load-more, and multi-select resolution are not
part of this integration. The optional React producer helper is exported from
`@nickwelsh/zero-for-laravel/react/formbraid`.

## Creation defaults

Use `withAttributes` on the Eloquent creation builder or in a shared Eloquent scope to supply creation
defaults. By default it also adds equality conditions to reads:

```php
use App\Enums\ZeroContext;
use ZeroForLaravel\Context\ContextReference;

$query->withAttributes(['user_id' => ContextReference::current(ZeroContext::USER_ID)]);
// Read condition: user_id equals the resolved context value.
// Create default: user_id is that value.
// Explicit creation data can override it.
```

For a default without an owner-only read filter, pass `asConditions: false`:

```php
// Inside TodoList's global scope: filter by membership.
// Set the creator without an owner-only read condition.
$query->whereHas('memberships')
    ->withAttributes(
        ['user_id' => ContextReference::current(ZeroContext::USER_ID)],
        asConditions: false,
    );
```

Effective creation data merges in this order, with later values winning:

1. Active global scope defaults, in registry order (inherited, attributes, boot).
2. Root query and local scope defaults, in call order.
3. Explicit creation data, including a deliberately supplied null when allowed.

For example, an authorized Zero controller action can add root defaults, then
override a default with explicit data:

```php
$todo = Todo::query()
    ->withAttributes(['completed' => false])
    ->create([
        'list_id' => $data['list_id'],
        'title' => $data['title'],
        'completed' => true,
    ]);
// completed is true; the explicit creation data wins.
```

Defaults do not turn arbitrary `where` predicates into creation data. Nested
predicate callbacks and higher-order OR scopes contribute conditions only, not
parent defaults. Related queries also keep their defaults separate. Removing a
global scope removes both its constraints and its defaults.

Global creation defaults apply to Zero creates, including controller
`Todo::create($request->validated())` lowered by the checked compiler and the create
branches of mutation helpers such as `insertUnlessExists` and `upsertUnique`.
An existing-row/update branch is never stamped with creation defaults. Ordinary
Eloquent creates outside Zero are untouched; Zero scopes are not model events.

A field omitted from FormRequest `$request->validated()` is **not caller input**
and does not block a default. This is useful for setting a list creator without
accepting `user_id` from a form. It is not immutable authorization: trusted code
can explicitly supply a different value, and a default never proves that an actor
may assign a user or attach a todo to a list. Keep mass-assignment constraints,
policies, Gates, and FormRequest association checks. Updates never receive these
defaults, so authorize any explicit ownership changes separately.

Browser defaults use typed provider context; Laravel resolves its own trusted
context for authoritative defaults. Do not infer additional optimism from arbitrary
FormRequest normalization, observers, or events. Use explicit portable operations,
a custom projection, or disabled optimism for nonportable behavior.

Use `conceal: true` for actions that must normalize private-resource errors. Keep
external effects server-only and use a transactional outbox plus idempotent workers
when delivery must survive process failure. See [shared operations](./shared-operations.mdx).
