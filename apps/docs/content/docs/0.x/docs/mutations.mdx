---
title: Controller mutations
description: Compile typed controller actions into native optimistic and authoritative execution.
---

Explicitly annotate an action on a registered Laravel route:

```php
use ZeroForLaravel\Attributes\ZeroMutation;

/** @return array{id: string} */
#[ZeroMutation]
public function store(StoreTaskRequest $request): array
{
    $task = Task::create($request->validated());

    return ['id' => $task->id];
}
```

The authoritative FormRequest retains preparation, authorization, rules, and
validation hooks. Arbitrary FormRequest hooks and Eloquent events do not
automatically run in optimistic JavaScript. Generated prediction covers only the
checked portable subset; use custom or disabled optimism when nonportable PHP
changes the intended local result.
Annotated actions are native-only: ordinary HTTP requests to their route return
405 instead of bypassing stable preparation or invoking a second write path.
Real route middleware and binding run at the authoritative boundary. Call Gates
and policies explicitly in the action or its request; an attribute is not a grant
of permission. Reload and lock state-dependent bound records with
`$mutation->reloadForUpdate($task)` before reauthorization and writes.

One checked operation tree generates native client execution and authoritative
Eloquent execution. Prepared IDs and timestamps are reused across replay and
delivery. Metadata stays separate from mass-assignable input. Unsupported shared
PHP fails generation rather than silently disappearing.

## Optimism strategies

- `#[ZeroMutation]`: generated prediction from supported PHP.
- `#[ZeroMutation(optimism: 'custom')]`: an explicitly supplied native projection.
- `#[ZeroMutation(optimism: 'disabled')]`: enqueue without speculative writes.

All three use the same native protocol, validation, results, and lifecycle. Pass
custom projections to the generated `createControllerMutationBindings` factory.
When a custom action exists, the React module exports `createZeroBindings(projections)`
instead of constructing a provider without the required projections. Call it once
in an application-owned module and export its `ZeroProvider` and `actions`.
Key each projection by the imported action's literal `action` property, for example
`createZeroBindings({ [notify.action]: async ({ tx, args }) => ... })`, rather than
typing a PHP controller path by hand.
Declare their client result independently when it differs from the server result.
Missing required bound rows produce the declared pre-write no-op prediction;
the valid intent still reaches Laravel.

## Client invocation

```tsx
import { useControllerMutation } from '@nickwelsh/zero-for-laravel/react';
import { store as create } from '@/zero/App/Http/Controllers/TaskController';

const createTask = useControllerMutation(create);
const saved = await createTask({ title: 'A task' });
console.log(saved.id);
```

Exports follow the PHP namespace and method name. Each controller module also
exports named input and result types, such as `StoreInput` and `StoreResult`.
The same imports work with custom optimism: the hook uses the bindings installed
by the current generated `ZeroProvider`, including its custom projections.

## Prepared fields

Generated creates prepare identities and time **before** calling `zero.mutate`.
`HasUuids` selects UUID generation; `HasUlids` selects ULID generation. Eloquent's
timestamp settings determine the created/updated columns, including renamed
`CREATED_AT` and `UPDATED_AT` columns. Auto-incrementing keys are not supported
for generated creation. These values stay outside FormRequest business input:
forms send fields such as `title`, not required IDs or timestamps.

Preparation runs once per submission. The frozen native arguments carry the same
values through optimistic execution, replay, and authoritative PHP execution.
Updates preserve creation time and use the prepared time for the updated column.
Server authorization and format validation still apply; client time is not a
trusted audit clock. Arbitrary server-only Eloquent creates in custom/disabled
actions are not automatically transformed into client-prepared creates.

Override generators globally when constructing the generated provider:

```ts
import { v7 as uuid } from 'uuid';
import { createZeroBindings } from '@/zero/generated.react';

export const { ZeroProvider } = createZeroBindings({ uuid, now: () => new Date() });
// With custom optimism: createZeroBindings(projections, { uuid, now: () => new Date() }).
```

Or pass overrides as the hook's third argument:
`useControllerMutation(create, {}, { uuid, now: () => new Date() })`.
The supported generators are `uuid`, `ulid`, and `now`. Overrides must return valid,
distinct identities and a valid nonnegative date. Never generate values inside an
optimistic projection: Zero can replay it more than once.

Supply route arguments for bound actions. For direct native control, prepare once
with a binding from `createControllerMutationBindings`, using
`binding.prepare(input, routeArguments, preparation)`, then call `zero.mutate(request)`.
`.client` means local application; `.server` means authoritative outcome. Parse
result data with the generated client/server result schemas. `void`, explicit
null, and structured JSON remain distinct. Model and HTTP-response serialization
are not implicit result contracts.

The hook tracks pending state, field errors, local application, server acceptance,
and committed-but-undecodable results separately. Navigate and show authoritative
success only after server acceptance. Unmounting stops observation, not the queued
write. Unmodified Inertia forms do not automatically submit through Zero.

Business changes, native progress, and returned data commit atomically. Application
rejections roll back business writes and persist an error outcome. Duplicate
delivery does not rerun the action; a lost callback response can recover through
native persisted results. These are not durable JavaScript promises across reloads.

## Formbraid 0.2

Use Formbraid's normal descriptor API in a React 19 app:

```tsx
import { store, update } from '@/formbraid/zero/App/Http/Controllers/TodoListController';
import { Form } from '@/formbraid';

<Form form={store} />;
<Form form={update({ list: list.id })} defaultValues={{ name: list.name }} />;
```

Install `formbraid/laravel`, `@formbraid/core`, and `@formbraid/react` at `^0.2.0`,
and `effect` at `4.0.2`. Run `php artisan formbraid:init` to scaffold the
application-owned registry and components. Register a build-only Zero producer
instead of the scaffold's HTTP Laravel producer:

```ts title="resources/js/formbraid/zero.ts"
import type { Integration } from '@formbraid/core/vite';

export default {
    name: 'zero',
    registry: new URL('./index.ts', import.meta.url),
    metadata: new URL('./_metadata.json', import.meta.url),
    command: ['php', 'artisan', 'zero:formbraid'],
    watch: ['app/**/*.php', 'routes/**/*.php', 'config/zero.php', 'config/formbraid.php'],
    outputs: ['resources/js/formbraid/zero/**', 'resources/js/zero/**', 'app/Formbraid/FormField.php'],
} satisfies Integration;
```

```ts title="vite.config.ts"
import { vitePlugin as formbraid } from '@formbraid/core/vite';
import zeroForms from './resources/js/formbraid/zero';

// Alongside the application's other Vite plugins:
formbraid({ integrations: [zeroForms] });
```

Vite inspects the component registry and writes metadata before running Artisan.
`zero:formbraid` reuses Formbraid's request extraction, field/group generation,
component enum, and hash-owned publication. It refreshes native Zero contracts and
the React provider, then emits definitions and callback-backed controller forms
under `zero.formbraid_output` (default `resources/js/formbraid/zero`). Only
`#[ZeroMutation]` actions with one FormRequest produce forms. Parameterless actions
export descriptors; actions with model/scalar route arguments export factories.
There is no Zero-specific form hook or replacement `Form` component.

Zero actions are native-only: do not use Formbraid's Fetch/Inertia controller
descriptors for them. Ordinary HTTP forms may still use the Laravel producer in a
separate output directory.

Formbraid owns the editable draft, validation, errors, defaults, and submission
lifetime. Zero owns preparation, optimistic replay, and the durable write. The
generated callback resolves the application's connection only at submission,
reuses its registered bindings/preparation, and retains the authoritative result type.

The default runtime comes from `zero/generated.react.ts`. For application-owned
bindings, set `zero.formbraid_runtime` to their project-relative TypeScript module;
export `controllerRuntime` alongside `ZeroProvider` from the same
`createZeroBindings(projections, preparation)` result. Static descriptors require
one active Zero session per binding; ambiguous clients are rejected rather than
selecting another user's connection. Separate applications can use separate binding instances.

Initialize defaults through `<Form defaultValues={values} />`. Formbraid's own
`useForm(store, options)` remains available when programmatic reset or instance
access is useful. Use a key or explicit reset when switching records; rerenders
must not reset edits.

Success includes the decoded authoritative result as `result.value` in Formbraid's
`onResult`. Local optimistic completion alone does not settle the form. Laravel
field/root errors and generated input-codec errors become `invalid`; other errors
become `failure`. A committed result-decoding failure remains a
`MutationResultError` with `committed: true`: show the warning without retrying the
write automatically. Cancellation or unmount stops observation and suppresses
late outcomes, but cannot undo an enqueued mutation. An already-aborted submission
does not enqueue a write. This transport does not report upload progress or add a
file-upload path to Zero's JSON mutation protocol.

The todos example consumes generated create-list and add-todo descriptors with
application-owned components. Optional producer utilities live in
`@nickwelsh/zero-for-laravel/formbraid`; application components need not import them.
Zero's ordinary entry points do not load Formbraid or Effect.

## Creation defaults

Use `withAttributes` on a Zero query or in a Zero scope to supply creation
defaults. By default it also adds equality conditions to reads:

```php
use App\Enums\ZeroContext;

$query->withAttributes(['user_id' => ZeroContext::USER_ID]);
// Read condition: user_id equals the resolved context value.
// Create default: user_id is that value.
// Explicit creation data can override it.
```

For a default without an owner-only read filter, pass `asConditions: false`:

```php
// Inside TodoList's global scope: filter by membership.
// Set the creator without an owner-only read condition.
$query->whereHas('memberships')
    ->withAttributes(
        ['user_id' => ZeroContext::USER_ID],
        asConditions: false,
    );
```

Effective creation data merges in this order, with later values winning:

1. Active global scope defaults, in registry order (inherited, attributes, boot).
2. Root query and local scope defaults, in call order.
3. Explicit creation data, including a deliberately supplied null when allowed.

For example, an authorized Zero controller action can add root defaults, then
override a default with explicit data:

```php
$todo = Todo::zeroQuery()
    ->withAttributes(['completed' => false])
    ->create([
        'list_id' => $data['list_id'],
        'title' => $data['title'],
        'completed' => true,
    ]);
// completed is true; the explicit creation data wins.
```

Defaults do not turn arbitrary `where` predicates into creation data. Nested
predicate callbacks and higher-order OR scopes contribute conditions only, not
parent defaults. Related queries also keep their defaults separate. Removing a
global scope removes both its constraints and its defaults.

Global creation defaults apply to Zero creates, including controller
`Todo::create($request->validated())` lowered by the checked compiler and the create
branches of mutation helpers such as `insertUnlessExists` and `upsertUnique`.
An existing-row/update branch is never stamped with creation defaults. Ordinary
Eloquent creates outside Zero are untouched; Zero scopes are not model events.

A field omitted from FormRequest `$request->validated()` is **not caller input**
and does not block a default. This is useful for setting a list creator without
accepting `user_id` from a form. It is not immutable authorization: trusted code
can explicitly supply a different value, and a default never proves that an actor
may assign a user or attach a todo to a list. Keep mass-assignment constraints,
policies, Gates, and FormRequest association checks. Updates never receive these
defaults, so authorize any explicit ownership changes separately.

Browser defaults use typed provider context; Laravel resolves its own trusted
context for authoritative defaults. Do not infer additional optimism from arbitrary
FormRequest normalization, observers, or events. Use explicit portable operations,
a custom projection, or disabled optimism for nonportable behavior.

Use `conceal: true` for actions that must normalize private-resource errors. Keep
external effects server-only and use a transactional outbox plus idempotent workers
when delivery must survive process failure. See [shared operations](./shared-operations.mdx).
