---
title: What works with Zero for Laravel
description: Which models Zero can sync, which PHP operations it can translate, and which decisions stay on the server.
---

## Which models can I sync?

Use one upstream database connection and unprefixed tables in the `public` schema.
Use one model per table and give each model a unique short class name, even across
namespaces. Pin the Zero client and `zero-cache` to **1.11.4**.

Add `HasZeroQueries` to each [model](./models.mdx) you want to sync. For example,
to include a task's comments, both `Task` and `Comment` must opt in. Declaring
the Eloquent relationship doesn't publish `Comment` or expose hidden foreign
keys. If a required key is missing from the published columns, generation fails.

## Which PHP operations can Zero translate?

- **Queries:** [`ZeroQuery`](./queries.mdx) builds native Zero queries (ZQL), not
  arbitrary Eloquent SQL. Use `with()` to include related rows and `whereHas()`
  to filter parent rows. Clone a builder before using it for independent branches.
  The generator checks local and global Eloquent scopes and relationship filters;
  it rejects a filter it can't translate rather than returning unfiltered rows.
- **Request context:** Declare [context fields](./configuration.mdx#typed-context-and-resolver)
  as cases of a string-backed enum. Give each case one public `#[ResolvesContext]`
  method with a scalar or nullable scalar return type. Generation reads the type
  without running the resolver.
- **Mutations:** [Generated actions](./mutations.mdx) support checked expressions,
  branches, bounded loops over keyed items, shared helpers, transaction reads and
  writes, authorization guards, and JSON results. Unsupported controller code
  fails generation. A redirect action needs one final supported `RedirectResponse`
  return even if the browser doesn't predict it. Use an ordinary HTTP route for
  other response types.
- **New rows:** Generated creates use UUIDs or ULIDs; repeated creates in a keyed
  loop use UUIDs. For a database-assigned numeric ID, create the row on the
  server with optimism disabled. Zero doesn't replace temporary client IDs with
  database IDs.

The generator doesn't translate soft deletes, arbitrary custom casts, or dynamic
helper calls. Nullable or partial unique keys and atomic writes across database
connections aren't supported.

## What stays on the server?

**Laravel decides whether a write is allowed.** The browser can predict a result,
but it doesn't run arbitrary middleware, policies, Gates, FormRequest hooks,
validation, or model events. Use [custom or disabled optimism](./mutations.mdx#optimism-strategies)
when a write depends on behavior the browser can't reproduce.

A row missing from the browser cache may still exist on the server. If a prediction
needs that row, it can skip its local writes and let Laravel handle the request.
Make that decision before the first write: there is no automatic savepoint for
undoing part of a prediction. [Typesense search](./authorization.mdx#who-can-see-search-results)
also needs its own access filter; Zero's row permissions don't filter the search index.

For external work such as sending email, arrange delivery after commit and make
retries safe (for example, with an outbox and an idempotency key). Recovering a
mutation outcome doesn't restore a JavaScript promise after reload or give the
user a persistent inbox.

Deploy generated PHP and TypeScript together. Each generated operation name
includes a fingerprint of its contract, so a stale client request is rejected
rather than run with a different meaning.
