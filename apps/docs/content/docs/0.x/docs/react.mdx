---
title: React and Inertia
description: Inject controller-declared live props into plain React page components.
---

Run `php artisan zero:generate --react`. It writes the bound provider and creates
an application-owned `zero.config.ts` once. Set the public cache URL there; never
put the cache API key in browser configuration.

Install the query bindings in Inertia's page resolver:

```tsx
import { createInertiaAdapter } from '@nickwelsh/zero-for-laravel/inertia';
import { bindings } from '@/zero/generated.queries';

const livePages = createInertiaAdapter(bindings);
// After loading the requested component in createInertiaApp.resolve:
return livePages.wrap(module.default, page);
```

Put the generated `ZeroProvider` in the authenticated persistent layout, outside
the wrapped page. Supply user identity and the context counterpart used for local
prediction. Laravel independently resolves trusted context. Identity or tenant
changes isolate subscriptions and local storage; native Zero owns construction
and cleanup.

```tsx
import type { InferLiveQueryResult } from '@nickwelsh/zero-for-laravel';
import type { Data } from '@nickwelsh/zero-for-laravel/react';
import type { index } from '@/zero/App/Http/Controllers/TaskController';

export default function Tasks({ tasks }: { tasks: Data<InferLiveQueryResult<typeof index.tasks>> }) {
    if (tasks.status === 'loading') return <p role="status">Loading tasks…</p>;
    if (tasks.status === 'failure') return <p role="alert">Unable to load tasks.</p>;
    return tasks.data.map((task) => <p key={task.id}>{task.title}</p>);
}
```

There is no generated global page namespace. Define page props in your application
and infer live data from the exported queries. Ordinary props remain application-owned.

## Native Zero access

The generated hook returns the actual, schema-typed Zero instance. Query factories
produce native requests, usable by `run`, `preload`, `materialize`, or Zero's `useQuery`:

```tsx
import { useQuery } from '@rocicorp/zero/react';
import { useZero, actions } from '@/zero/generated.react';
import { index } from '@/zero/App/Http/Controllers/TaskController';
import { store } from '@/zero/App/Http/Controllers/TaskController';
import type {
    InferQueryInput,
    InferQueryResult,
    InferMutationInput,
    InferMutationResult,
} from '@nickwelsh/zero-for-laravel';

const zero = useZero(); // Inside a component under ZeroProvider.
const [tasks] = useQuery(index.tasks({}));
const rows = await zero.run(index.tasks({}));
const submission = zero.mutate(actions[store.action].prepare({ title: 'New task' }));
await submission.client;
const outcome = await submission.server;

type QueryInput = InferQueryInput<typeof index.tasks>;
type QueryResult = InferQueryResult<typeof index.tasks>;
type CreateInput = InferMutationInput<typeof store>;
type CreateResult = InferMutationResult<typeof store>;
```

Supply the inputs required by your controller. Native queries preserve wire-format
values, including numeric timestamps. `index.tasks.live(input)` instead returns the
selection accepted by `useData`, whose dates are decoded to `Date`. Its row type is
`InferLiveQueryResult<typeof index.tasks>`. Neither path requires an Inertia page.

Mutation requests must come from the bindings registered with that Zero instance.
The generated provider exports its `actions` and native `mutators`; applications
with custom projections obtain both from their `createZeroBindings(projections)`
result. Outside React, use `createControllerMutationBindings` from `.mutations.ts`
and pass its `mutators` to `new Zero`. No React lifecycle or global singleton is
required by that factory. `useZero` follows native lifecycle semantics and must run
under the initialized provider, not the pre-initialization Inertia shell.

`InferMutationResult` describes the decoded authoritative result. Native `.server`
returns a success/error envelope; on success, parse its `data` with the action's
`serverResultSchema`, or use the binding's `execute` helper. Optimistic `.client`
results can differ from authoritative results.

No per-prop `useQuery` is necessary. Rows and related rows are plain decoded data,
without a `.data` wrapper or mutation methods. Live objects distinguish loading,
refreshing, success, stale data, failure, and idle/disabled state. Connection status
does not imply query completeness.

Infinite props expose `loadMore`, `hasMore`, and loading state; cursor-page props
expose navigation. Completion determines whether more data is known to exist.
Partial reloads and history use reserved page metadata; query descriptors never
replace the omitted live prop in serialized page props. Initial SSR and hydration
render a deterministic loading shell before native client initialization.

Use [controller mutation bindings](./mutations.mdx) for forms. Pages do not receive
model objects with bound write methods. See the shared todos example for the full
resolver, layout, connection options, forms, and sharing workflow.
